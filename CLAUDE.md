# Kate-Code Plugin

A Kate text editor plugin that wraps Claude Code using claude-agent-acp.

## Build Instructions

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
```

## Installation

Test install:
```bash
cmake --install build --prefix ~/.local
```

Then restart Kate and enable the plugin via:
Settings > Configure Kate > Plugins > Enable "Kate Code"

## Architecture

### Layer Structure
- **Plugin**: KateCodePlugin, KateCodeView - Kate integration
- **ACP**: ACPService, ACPSession - JSON-RPC 2.0 over stdin/stdout to claude-agent-acp
- **MCP**: MCPServer - Built-in MCP server executable for Kate editor tools
- **UI**: ChatWidget, ChatWebView, ChatInputWidget, PermissionDialog, SessionPanel
- **Util**: KDEColorScheme - reads ~/.config/kdeglobals

### Key Files
- `src/plugin/KateCodePlugin.{h,cpp}` - Plugin registration via K_PLUGIN_CLASS_WITH_JSON
- `src/plugin/KateCodeView.{h,cpp}` - Per-window view: opens chats as editor-area tabs, side panel session list, provides Kate context
- `src/acp/ACPService.{h,cpp}` - QProcess-based claude-agent-acp subprocess management
- `src/acp/ACPSession.{h,cpp}` - Protocol flow and session state management
- `src/acp/ACPSessionDeleter.{h,cpp}` - Deletes saved sessions on the agent's side (one-shot agent process)
- `src/acp/AgentInstaller.{h,cpp}` - Installs ACP registry agents into Kate Code's folder on a remote host or on this computer; `findLocalExecutable()` is how local agents are found
- `src/acp/RemoteHelper.{h,cpp}` - Kate Code's helper (kate-code-helper) on the host of a remote agent: install, launch, digests, watches (see "kate-code-helper")
- `src/acp/ACPModels.h` - Data structures (Message, ToolCall, TodoItem, etc.)
- `src/remotefs/RemoteLocation.{h,cpp}` - Static lib `kateremotelocation`: remote URL <-> `<MountRoot>/<scheme>/<authority>/<path>` mapping, ssh authority validation, symlink target rewriting, ssh command lines (terminal, agent) and the askpass environment; shared by kate-remote-fs, the plugins and Kate Code
- `src/remotefs/RemotePathMap.{h,cpp}` - (in `kateremotelocation`) path translation between a host's directory under the mount root and the host's own paths, for agents running on the host (JSON messages both ways)
- `src/remotefs/daemon/` - `kate-remote-fs` FUSE daemon (libfuse3 high-level API) with DBus interface `org.kde.KateRemoteFS`; systemd user unit + DBus activation file
- `src/remotefs/askpass/main.cpp` - `kate-remote-fs-askpass`: SSH_ASKPASS for the mounts, login passwords from kpasswdserver (KIO's password cache)
- `src/remotefs/autotests/` - QtTest unit test and `test_remotefs.py` integration test (with `kpasswdtool` to seed kpasswdserver, `acpdriver` to run Kate Code's `ACPService` against a fake remote agent) (ctest; runs under `dbus-run-session`, sandboxed `sftp-server` via bwrap as the remote)
- `src/remoteprojects/` - "Remote Projects" Kate plugin (`kateremoteprojects`): File > Open Remote Folder… (KDE's folder dialog via `QFileDialog::getExistingDirectoryUrl`, starting at `remote:/` (network folders), schemes sftp/remote/file; KIO browses, the result is handled here: a `remote:` link is resolved with `KIO::stat` → `UDS_TARGET_URL`) / Open Recent Remote Folder, opens `<MountRoot>/<scheme>/<authority>/<path>` as a project via the project plugin view's `openDirectoryOrProject(QDir)` slot; `RemoteTerminal.{h,cpp}`: the "Remote Terminal" bottom tool view (`RemoteTerminalPanel`, one Konsole part per remote folder on an ssh host)
- `remote-helper/` - `kate-code-helper`, Kate Code's optional helper on remote hosts: a separate CMake project (not in the plugin's build), released through its own GitHub workflow; see "kate-code-helper" below
- `src/mcp/MCPServer.{h,cpp}` - MCP protocol handler (initialize, tools/list, tools/call)
- `src/mcp/main.cpp` - MCP server entry point (stdio JSON-RPC loop); `--http` mode for remote agents
- `src/mcp/MCPHttpServer.{h,cpp}` - MCP Streamable HTTP transport (token, 127.0.0.1) of kate-mcp-server, reached by remote agents through `ssh -R`
- `src/ui/ChatWidget.{h,cpp}` - Main chat interface with ACP integration (one per editor tab)
- `src/ui/SessionPanel.{h,cpp}` - Side panel listing the window's open chats with status and usage
- `src/ui/ChatWebView.{h,cpp}` - QWebEngineView for HTML/CSS/JS rendering
- `src/ui/ChatInputWidget.{h,cpp}` - Multiline text input with send button
- `src/ui/PermissionDialog.{h,cpp}` - Modal dialog for tool approval requests
- `src/config/SettingsStore.{h,cpp}` - QSettings + KWallet storage, ACPProvider management
- `src/config/KateCodeConfigPage.{h,cpp}` - Kate config page with provider table, diff colors, summaries
- `src/util/KDEColorScheme.{h,cpp}` - KDE color extraction from kdeglobals
- `src/web/chat.{html,css,js}` - Web assets for chat interface
- `src/katecode.qrc` - Qt resource file for web assets
- `src/katecode.json` - KPlugin metadata

## Lessons Learned

### Build System
- Must include `<KLocalizedString>` for i18n() function
- KF6 components needed: I18n, TextEditor, CoreAddons, XmlGui
- Qt6 components: Core, Widgets, WebEngineWidgets

### Plugin Structure
- Chats are editor-area widgets added with `KTextEditor::MainWindow::addWidget()` (Kate owns and deletes them; they can move between splits). Kate calls an invokable `bool shouldClose()` before closing such a tab
- The side panel (`createToolView()` with `KTextEditor::MainWindow::Left`) holds the session list
- Several chats can run agents at once. Each chat owns an `EditorSession` DBus endpoint (`/KateCode/Session/sN`, interface `org.kde.katecode.Editor`); its kate-mcp-server gets the path in `KATECODE_DBUS_PATH` (service name in `KATECODE_DBUS_SERVICE`), so questions and edit notifications reach that chat only. The shared `/KateCode/Editor` object only serves document tools
- Agent actions must not open, close or activate windows/tabs or move focus, nor show modal dialogs (a dialog during a DBus call nests an event loop and times the agent out). Document writes (`EditorDBusService::changeDocument()`, `ACPSession::handleFsWriteTextFile()`) change an open document's buffer and save it only when its file is unchanged on disk (`EditorDBusService::documentChangedOnDisk()`: Kate's `modifiedOnDisk` flag, tracked per document, or the git-blob digest of the file vs `Document::checksum()`, since Kate updates the checksum when it notices a change); an unmodified stale buffer is written on disk and reloaded, a modified one is refused. Files that are not open are written on disk (QSaveFile), never opened
- Prompts: a slash command (`ACPSession::isSlashCommand()`: a `/name` first word naming one of the agent's `available_commands_update` commands, or any `/name` before the agent sent its list; decided once, when sent) is sent alone as one text block (agents only recognise a command that is the whole prompt; editor context and the first-prompt `<system-reminder>` wait for the next ordinary prompt). While a turn runs, other messages are sent as further `session/prompt` requests when the agent advertises `agentCapabilities._meta.claudeCode.promptQueueing` (Claude Code folds them into the running turn at its next step; the turn ends when all have answered, `m_midTurnPromptIds`); otherwise, and for commands, they are queued until the turn ends. (`_session/steering` is not used: it aborts the current generation)
- Work outside a prompt (claude-agent-acp; `agentCapabilities._meta.claudeCode` marks it, `ACPSession::m_claudeCodeAgent`): Kate Code advertises display terminals (`clientCapabilities._meta.terminal_output: true`, Zed's extension). A command's tool call then carries `_meta.terminal_info` (tool_call), `terminal_output` (`{terminal_id, data}`, appended; sent before the final status, so `handleDisplayTerminal()` gives it as the result, again with the final status for the transcript) and `terminal_exit` (`exit_code`, null when unknown); its `content` `{type: terminal}` is not linked to Kate Code's terminal panel (`isAgentDisplayTerminal()`: `_meta.terminal_info` in the update, or the terminal id is the tool call's id and not a `TerminalManager` terminal: later updates, e.g. a replayed result, may leave `terminal_info` out). A command that went to the background: its result names the task (`_meta.claudeCode.toolResponse.backgroundTaskId`), the call completes without `terminal_exit`, and the exit comes when the command ends, also after the turn (`backgroundCommandCount()`, the tool call's "running/finished in background" badge, the status row's "◐ Command running in the background" instead of "Waiting for your input"). On the v1 core only background Bash commands are signalled: no live output (v2 only), and `Monitor`/`Workflow` calls complete at once. When a background task ends Claude Code starts a cycle on its own: its output arrives outside a prompt; the first `agent_message_chunk`/`agent_thought_chunk` (thinking is not shown, but may be all there is for a while)/`tool_call` then (not while replaying, summarising, or before a cancelled prompt has answered (`m_cancelledPromptId`), only for Claude Code) opens an assistant message (`auto_N`, recorded in the transcript; the status row shows working, Stop sends `session/cancel` and emits `promptCancelled()`; permission requests show as during a prompt), which ends at the cycle's result (the `usage_update` with `cost`/`_meta._claude/origin`, e.g. `{kind: task-notification}`; mid-turn usage reports have neither), at the next prompt (Claude Code folds it into the cycle) or at Stop. A result while one of the cycle's tool calls has no final status (`m_cycleToolCalls`) does not end it: Claude Code (2.1.274+) answers task notifications that came together with one follow-up and sends a placeholder result (`num_turns: 0`, empty, before the follow-up runs) for all but the last, and the adapter forwards its `usage_update` like a real one (no `num_turns`; it was seen ending a cycle while a long foreground command ran, so the status said "Waiting for your input"). A placeholder between steps (no tool call running) still ends it; the next text, thinking or tool call opens a new cycle (a new `auto_N` message). A tool call that never gets a final status keeps the cycle open until Stop or the next prompt. Updates of a tool call go to its own message (`m_toolCallMessages`): the exit of a background command and a stopped cycle's tool call (reported failed after the cycle's result) come later. `session/cancel` does not stop background commands (checked with the real agent). Checked with the real claude-agent-acp 0.106 (a scratch driver logging the wire: foreground/background Bash, the cycle, `session/cancel` with only a background command and during a cycle; an offscreen Kate with Haiku: status working → background → waiting, the badge, the cycle's message, the transcript) and in an offscreen Kate with a stand-in agent (the same shapes; a permission request in a cycle answered; Stop during a cycle; a cancelled prompt's late output not shown); loading a real session with a background command (no terminal panel, no badge, output as the result), not in ctest. Placeholder results checked in an offscreen Kate with a stand-in agent (one while a tool call runs: still working; one between steps: waiting until thinking reopens it), not with the real agent. Not seen: a cycle that ends in an error. Messages typed in another client of the session (Claude Code's Remote Control: claude.ai, the mobile app) come as `user_message_chunk` outside a replay (claude-agent-acp's v1 `isRemoteHumanMessage()`; it never sends Kate Code's own prompts back), only handled for Claude Code: shown at once as a user message (`remote_N`; further blocks right after it joined to it, context blocks left out as in replays) and recorded in the transcript at the agent's next update; during a prompt or a cycle what follows goes into a new assistant message below it (as for a mid-turn prompt), otherwise it opens a cycle. Checked against the adapter's source and in an offscreen Kate with a stand-in agent (idle and mid-turn, the transcript), not with Remote Control itself
- Agents for remote folders (below kate-remote-fs's mount root, ssh schemes sftp/fish) run on the host: see "Remote agents" below
- Never block a DBus call or ACP request in a nested event loop (other sessions' requests would nest inside it): askUserQuestion uses a delayed DBus reply, terminal/wait_for_exit a callback
- Each chat keeps its own provider; `ACP/activeProvider` is only the default for new chats
- Chats connect as soon as they are created (`ChatWidget::startSession()`); there is no Connect button. A failed or lost connection shows a Reconnect button in the chat (resumes the last connected session if any), and switching provider starts a new session
- Plan usage limits (`RateLimits`, `src/acp/RateLimits.{h,cpp}`): claude-agent-acp attaches Claude Code's rate-limit info to a `usage_update` as `_meta["_claude/rateLimit"]` (`unifiedWindows`: `{five_hour: {utilization (fraction, 0.04 = 4%), resetsAt (Unix seconds), status (allowed/allowed_warning/rejected)}, seven_day: ...}`; older: one window in `rateLimitType`/`utilization`/`resetsAt`/`status`), only when the values change (seen with 0.106: on a process's first turn, not on the next). `ACPSession::rateLimitsChanged` → `RateLimitStore` (per provider id, merged by window, shared by all chats since the limits are the account's, kept in the `kate-code` QSettings `RateLimits` group so a new chat or Kate shows them before the agent reports again). The chat's status row (`ChatInputWidget::setRateLimits()`) shows only the most immediate window ("5h usage 4%"; windows ordered by `RateLimits::windowRank()`), coloured by the worst window (orange: warning or 80%+, red: limit reached), all windows with reset times in the tooltip; a window past its reset shows 0% (a timer refreshes at the next reset); clicking (when connected) sends `/usage` (claude-agent-acp renders it from the SDK's usage API)
- Session titles come from the agent's `session_info_update.title`; renaming (header label double-click or rename button) sends `session/set_title` when the agent advertises `sessionCapabilities.title`, otherwise the title is kept locally. The title is shown in the chat header, the tab (`windowTitle`, elided) and the side panel. Kate follows a widget's `windowTitleChanged` in its tab but sets the window caption only when a tab is activated (`KateMainWindow::updateCaption()` is not a slot), so `KateCodeView` sets the caption (`KMainWindow::setCaption(title, false)`, as Kate does) when the active chat's title changes
- Provider logos (`AgentIcons`, owned by `SettingsStore`): explicit icon, else the ACP registry icon for the provider's `registryId` (fetched from cdn.agentclientprotocol.com, cached in `~/.cache/kate-code/acp-registry`, rendered with `currentColor` replaced by the palette text colour), else `code-context`. Kate reads a widget tab's icon only when adding the tab, so `ChatWidget::updateKateTabIcon()` finds the tab through a temporary unique title and sets the icon itself
- Resuming lives in the side panel (`SessionPanel`, filled by `KateCodeView::refreshResumableSessions()`): transcripts of the current project (or of all directories) with a user prompt, minus open sessions. The list is refreshed on view changes, on the project plugin's `projectFileNameChanged`/`projectMapChanged` (connected by name; it has no public header), when the panel is shown and by its refresh button; each refresh re-syncs `SessionStore`'s QSettings so other Kate instances' changes show up. Title, provider, first prompt and "replaced by" (context-injection restores start a new agent session) are kept per session in `SessionStore`; transcripts are only parsed for older, untracked sessions, since injected context embeds earlier transcripts. Resuming opens a new chat (`createChat(false)` + `ChatWidget::resumeSavedSession()`). With the provider's "True resume" (`ACPProvider::trueResume`, on by default; providers stored before were turned on once, `ACP/trueResumeDefaultOn`) it sends `session/load` when the agent advertises `agentCapabilities.loadSession`, else (and when the load fails) a new session gets the prior context (summary or Kate Code's transcript). claude-agent-acp loads any Claude Code session (also those of Zed or VS Code; loading appends a `cost-state` line to its `.jsonl`). While a `session/load` is pending (`ACPSession::isReplaying()`), the history the agent replays is shown: `user_message_chunk`s become user messages (a message's text blocks joined, `<system-reminder>` and editors' `<ide_…>` context blocks left out, Kate Code's injected "--- Previous session record ---" shown as a one-line note; checked against what the real claude-agent-acp replays for a VS Code and a Kate Code session), agent text and tool calls go into one assistant message per turn (ids `replay_N`: the first prompt after a load still gets the editor reminder), without a live turn's side effects (no diff highlights, remote host holds or document checks; the transcript only starts once the session is loaded). Sessions started elsewhere: a "Started elsewhere" section at the end of the side panel, collapsed by default (listing starts agents): when expanded (and on the refresh button), `KateCodeView::refreshElsewhere()` runs `ACPSessionLister` (`src/acp/ACPSessionLister.{h,cpp}`: one-shot agent like `ACPSessionDeleter`, `initialize`, then `session/list` pages up to 200 sessions when `sessionCapabilities.list` is advertised; a remote agent's `cwd`s come back as local paths) for every installed provider at once (remote folder: every provider, run on the host one after another, stopping at an ssh failure (exit 255); missing agents and agents that cannot list are skipped quietly, other failures shown) with the current directory as `cwd` (all-directories mode: no filter, local agents from `$HOME`). Results are cached per location and filtered on every panel refresh: Kate Code's own sessions (those its list shows: a transcript with a prompt, or a recorded first prompt; one opened from here but never prompted stays under "Started elsewhere"), open ones and the summariser's (`SummaryGenerator::ownAgentSessions()`, QSettings `Summaries/agentSessions`; the summariser also deletes its agent session with `session/delete` when it can) are left out, the same session through two providers is shown once. Opening one: `KateCodeView::resumeElsewhereSession()` → `ChatWidget::resumeSavedSession(..., load = true, listedTitle)`: always `session/load` (a reconnect loads it again), whatever the provider's true resume setting; the chat takes the title the agent listed it with (stored with the session once loaded, unless one is stored already; a title the agent sends replaces it). Tested: `test_remotefs.py` `test_session_list` (`acpdriver --list`: pages and the limit, paths both ways for a remote agent, a missing agent and one without `session/list` reported as unavailable), an offscreen Kate with a stand-in agent (a real click on the heading expands it (the toggle is queued: rebuilding inside the view's click handling would delete the clicked item), nothing is started before; the summariser's session left out; Enter opens one with session/load, titled as listed; the replayed history shown and cleaned; still listed after a restart until prompted; the first prompt carries the editor reminder; then it moves to Kate Code's own list, with that title). Not run: the summariser's session/delete Deleting (`KateCodeView::deleteSavedSession()`, panel context menu or Delete key) removes the transcript, summary and stored entry of the session and of the sessions it replaced; with the user's consent it also runs the agent headlessly (`ACPSessionDeleter`: `initialize`, then `session/delete` if `sessionCapabilities.delete` is advertised)
- Kate keeps the enabled-plugin list in the session file (`kate/anonymous.katesession`, `[Kate Plugins]`), not in `katerc`
- K_PLUGIN_CLASS_WITH_JSON macro requires katecode.json in same directory
- Plugin views are children of MainWindow and cleaned up automatically

### kate-remote-fs
- Paths mirror URLs under a stable, configurable root (`kate-remoterc` `[General] MountRoot`, default `~/.kate-remote`), so Kate's history (recents, session restore, projects; Kate resolves symlinks, so these must be real paths, not symlinks to the per-host mounts) survives reboots. kio-fuse's mount directory is random per run
- Backends: `sftp` hosts are `sshfs`; the KIO schemes (`KateRemote::kioSchemes()`, `[General] KioSchemes`, read once per process) go through kio-fuse: DBus `org.kde.KIOFuse.VFS.mountUrl("<scheme>://<authority>/")` (blocking call from the FUSE thread, may wait for a KIO login dialog) returns its per-run path, kept in `Mount::backendPath`; "unmounting" only closes our root fd (kio-fuse has no unmount); a dead kio-fuse gives `ENOTCONN` → remount (DBus activation restarts it). KIO hosts are mounted from their registered folders, not from `/` (the root of a WebDAV server is often not readable: Seafile `/seafdav`, Nextcloud `/remote.php/dav/files/<user>`): `mountUrl("<scheme>://<authority>/<folder>")` for each, and kio-fuse mounts from the first readable folder on the way (its "origin"; `/` when readable, so fish/smb hosts still show everything) and shows the folders above it as directories listing only what is mounted (names not mounted are ENOENT without asking the server). Folders are registered with DBus `addFolder(scheme, authority, path)` (registered host; mounted in kio-fuse first, so only working folders are kept; nested ones are not added; answered from a thread, may wait for a login), which the Remote Projects plugin calls for KIO folders when opening and when restoring session projects, and kept in the hosts file as `<scheme>/<authority>/<path>` lines (older daemons skip them). A registered folder that fails is logged and skipped; a KIO host without folders (registered before folders were) is mounted from `/`. A folder never opened through Remote Projects does not exist under the mount (open it once). kio-fuse's error messages have `strerror()` as Latin-1 (garbled in UTF-8 locales; kio-fuse `src/kiofuseservice.cpp`, `mountUrl()`, to be fixed upstream; the daemon only shows the text). Tested with a minimal WebDAV server in `test_remotefs.py` (`/` 404, shares at `/dav/` and `/deep/er/dav/`); tested by the user on a real password-protected WebDAV server (Seafile), password reuse included KIO authorities may have `;` in the user (smb `DOMAIN;user`). Tests drive KIO's `fish` worker through a fake `ssh` on the PATH given to bus-activated services
- Each sftp host is an `sshfs host:/` mount in `$XDG_RUNTIME_DIR/kate-remote-fs/<scheme>/<authority>`, mounted on first access (per-host state machine, waiters share one attempt, failures cached for `RetryAfterFailure`) and unmounted when idle with no open files. Operations use `*at()` calls on a held root fd of the live mount (checked `FUSE_SUPER_MAGIC`), never the plain directory; `ENOTCONN` (sshfs died) remounts and retries once (mount generation counter, not `fstat`, which may answer from cache)
- Only registered hosts exist (DBus `addHost`/`removeHost`/`hosts`, signal `hostsChanged`; kept in `~/.local/state/kate-remote-fs/hosts`, read at startup and written only by the daemon, so there is a single writer; `kate-remoterc` is user settings the daemon never writes): tools stat `HEAD` (git), `Cargo.toml`, `setup.py`... in every parent directory, and these are valid host names. Names are also validated strictly (`parseSshAuthority()`: no leading `-`/`.`); listing `sftp/` shows only connected hosts; creating/removing a host directory itself is refused without connecting
- sshfs runs without `reconnect`: it then exits when the connection drops, the next access gets `ENOTCONN` and remounts here, with failures cached (with `reconnect` every access to a vanished host waits for the connect timeout). Directory cache stays at sshfs's default 20 s (a cold cache is a round trip per file)
- Single instance via a lock file (`$XDG_RUNTIME_DIR/kate-remote-fs/lock`); the DBus name is taken only after mounting, so DBus activation / systemd `Type=dbus` readiness means the paths work
- Version (`BuildVersion.{h,cpp}` in `kateremotelocation`: project version + git commit at configure time, `KATE_REMOTE_BUILD_VERSION`): the daemon answers DBus `version()`. A package upgrade leaves the running daemon on the old code (the plugin did take the username from KIO while an old daemon ignored the password: that daemon predated password reuse). The plugin (`checkDaemonVersion()`, after `mountRoot`) warns in the first window's Output view when the daemon's `/proc/<pid>/exe` ends in " (deleted)" (replaced executable; works with daemons without `version()`), has no `version()`, or another version
- Restarting (after an update): unmounting the mount root ends the inotify watches on it, and Kate's are many: KTextEditor's KDirWatch on each open document (it reports the file as deleted, Kate's "deleted" bar, and never finds it again after the remount: tested), the project plugin's `QFileSystemWatcher` on `.kateproject`, `.git/index`, `.git/HEAD`. Inotify watches do not make a mount busy, so the kernel's check does not protect them. Hence holders: each Kate's Remote Projects plugin reports its open remote projects and documents (DBus `setOpenPaths(paths)`, local paths, debounced 300 ms after `documentCreated`/`documentWillBeDeleted`/`documentUrlChanged` and the project plugin's `projectAdded`/`projectRemoved` (by name), once at start even if empty, again whenever the daemon's name gets a new owner; without auto-start). The daemon (`RemoteFsService`, `QDBusContext`) records every calling connection (pid from the bus) and forgets it on disconnect (`QDBusServiceWatcher`, and a check that the name still has an owner before each decision): a connection with reported paths, or one that called this daemon instance without ever reporting (e.g. a Kate with an older plugin that called it; the restart request's own caller is exempt), blocks restarts. Not covered: programs that never call this instance yet hold watches on the mount (a Kate without the plugin, an older-plugin Kate that last spoke to the previous daemon, file managers, other editors). DBus `restart()` (Tools > Restart Remote Folder Service): empty, or "Not restarted: ..." naming the holders (`<comm> (pid N)` and up to 5 paths), or the processes keeping the mount busy (`processesUsing()`: cwd, root, fds, maps below the root). Every fallible check comes before the non-lazy `fusermount3 -u` of the root (`RemoteFs::unmountRootIfUnused()`: the kernel refuses while files are open or a working directory is below it), which is the point of no return; then `run()` returns and `main()` starts the installed executable: under systemd (its own `/proc/self/cgroup` names a `kate-remote-fs*.service` unit, never another unit, e.g. `dbus.service` when the bus started it) `systemctl --user --no-block restart <unit>` with `XDG_RUNTIME_DIR=/run/user/<uid>` (rather than an exec: systemd is assumed to stop a `Type=dbus` service whose bus name goes away, as during an exec; checked only with a `Type=simple` scratch unit, not the real `Type=dbus` one started by bus activation); otherwise `execv()` of the executable (same pid; the lock fd is `O_CLOEXEC`). Automatic: the idle timer restarts a daemon whose `/proc/self/exe` ends in " (deleted)" (the replacement existing) when no host is connected or connecting and no holders, two ticks in a row. The daemon running when this arrives is older (neither method): the plugin's action then shows the `systemctl` command. Tested: `test_remotefs.py` `test_restart` (refusals with a path and pid, an unreporting client, a busy working directory, the mount working after each; exec restart keeping hosts; the automatic restart of a replaced copy, blocked while a path is reported), an offscreen Kate in that sandbox (the built plugin reports documents and projects, a restarted daemon learns them again, no inotify watch of Kate left on the mount once closed, the action restarts it and Kate says so; against the installed older daemon the action shows the `systemctl` way), and a transient `kate-remote-fs-scratch.service` user unit with a private bus (restarted by systemd). Waiting for a restarted daemon in tests: ask the bus for the name owner's pid (`GetConnectionUnixProcessID`), never the daemon: the private bus would start the installed kate-remote-fs, which may take the lock first
- Lookups in one directory must not wait for a connecting host: request `FUSE_CAP_PARALLEL_DIROPS`, raise the worker thread cap (libfuse default 10)
- Symlinks: sshfs runs with `no_contain_symlinks` when supported (Arch patches sshfs to reject absolute/`..` links); `hostSymlinkTarget()` rewrites absolute targets and `..` above the remote root relative to the host directory, so links never resolve to local files
- sshfs drops ssh's stderr when daemonizing: the daemon passes `ssh_command=<SshCommand> -E <backend>/logs/<scheme>_<authority>.log` and reports that log; sshfs (without `-f`) exits only once mounted
- Helpers run without our fds (FUSE device, root fds: `CloseFileDescriptors`), with signals unblocked (the daemon blocks SIGTERM/INT/HUP for its signalfd) and in a new session (ssh asks through `SSH_ASKPASS`)
- Only ever unmount (`fusermount3 -u`) and `rmdir` backend dirs, never delete recursively: the mounts expose remote (and in tests local) files
- Qt logs to journald when stderr is not a terminal; tests set `QT_FORCE_STDERR_LOGGING=1`
- Passwords (`KdePasswords`, default on): sshfs's ssh gets `SSH_ASKPASS=kate-remote-fs-askpass` (`SSH_ASKPASS_REQUIRE=force`), with `KATE_REMOTE_AUTHORITY`, `KATE_REMOTE_FALLBACK_ASKPASS` (previous SSH_ASKPASS or ksshaskpass) and a per-attempt state file. ### Remote agents
- `ACPService::start(workingDir)` decides (so chats, resume and `ACPSessionDeleter` all follow): a folder that `locationForPath()` maps to an ssh scheme and `KateRemote::sshAgentCommand()` accepts (not fish `DOMAIN;user`, which keeps the local agent on the mount) runs the provider's agent through `ssh -T -o ServerAliveInterval=15 ... -- host "exec \"$SHELL\" -l -c 'cd <path> && exec env PATH=\"$PATH:$HOME/.local/bin:$HOME/bin:$HOME/.cargo/bin\" <agent> <args>'"` (login shell for the user's PATH; a local absolute executable path becomes its file name; unit-tested with sh/bash/zsh, fish when installed (not on the development machine); checked once against a real sshd with a zsh login shell). Killing the local ssh (`stop()`) ends the session: an agent reading stdin gets EOF and exits (checked over a real sshd). The ssh process runs in `$HOME`, not the mount. `SummaryGenerator` sets `setAllowRemote(false)` and runs in `$HOME` for remote projects (it only reads the transcript it is sent)
- Windows hosts (sftp drive paths `/C:/...`, `windowsPathForSftpPath()`): the remote command is `powershell -NoLogo -NoProfile -NonInteractive -EncodedCommand <base64 UTF-16LE>` of `windowsAgentScript()`, so sshd's default shell (cmd or PowerShell) passes it unchanged; the script checks the folder, adds `%USERPROFILE%\.local\bin`, `\bin`, `\.cargo\bin`, `%APPDATA%\npm` to PATH, finds the agent (`Get-Command -CommandType Application`: .exe/.cmd; exit 127 if missing) and runs it through `System.Diagnostics.Process` with stdin/stdout/stderr copied as bytes (PowerShell re-encodes native output it handles; stdin through an unbuffered FileStream, closed at end of input), exiting with its code. Arguments are quoted for `CommandLineToArgvW` (`windowsArgument()`). Kept short: cmd's command line limit is 8191 (unit test: < 7000). Unit-tested only (decoded script, quoting); not run on Windows here. `RemotePathMap` style Windows: the agent's `C:\a\b`/`C:/a/b`/`/C:/a/b` is `<hostDir>/C:/a/b`; the drive letter takes the folder's spelling; exact local paths go out as `C:\a\b`, paths in text up to the next space or quote, file URIs as `file:///C:/a/b`; UNC paths are left alone
- Passwords: `KateRemote::setSshAskpassEnvironment()` (shared with the daemon's sshfs): `kate-remote-fs-askpass` from the daemon's DBus `askpassProgram()` (login passwords from kpasswdserver, other prompts to `ksshaskpass`/the previous `SSH_ASKPASS`), state file `$XDG_RUNTIME_DIR/kate-code-askpass-<uuid>` per start, removed on exit/stop
- Paths: `RemotePathMap` in `ACPService`. Outgoing requests/notifications: every string has the local host directory (plain or as in a FullyEncoded `file://` URI) replaced by the remote path, at name boundaries (prompt text, resource URIs, `cwd`). Responses are not translated (file contents). Incoming messages: values of path keys (`path`, `paths`, `file`, `file_path`, `filePath`, `notebook_path`, `old_path`/`new_path`, `oldPath`/`newPath`, `cwd`, `uri`) that are absolute paths or `file:///` URIs get the host directory prepended, normalized (`..` stops at the remote root: never above the host directory); titles, commands and message text stay as the agent wrote them (ACPSession's title parsing maps them with `agentPath()`: relative ones against the remote working directory, confined the same way). Everything above the service sees local paths (edits, diffs, transcripts; session keys are the local mount paths, which mirror URLs)
- `ACPSession` for a remote agent: `clientCapabilities.terminal = false` and `terminal/create` answered with an error (never run its commands locally); `fs.readTextFile`/`writeTextFile` false, and `fs/*` requests answered with an error too: the agent changes files itself (shell commands), which the mount may show only after sshfs's cache expires (measured against a real host: about 1 s after the next open of the file, a stat does not count; until then sshfs answers from its cache, up to ~20 s; a re-read loop opens it all the time, hence its ~1 s), so reads through Kate could be stale and an Edit based on them undo a change. The configured stdio MCP servers are not passed (local programs). A remote editor reminder. Edits show as the tool calls' diffs in the chat only: edit tracking, in-editor diff highlights and jump-to-edit come from `fs/write_text_file`, so not for remote agents
- Kate's MCP tools for remote agents: `ACPService` (given the program and environment by `ACPSession::start()`: `KATECODE_DBUS_SERVICE`/`PATH` of the chat) runs `kate-mcp-server --http --remote-root <hostDir> [--remote-windows <drive>]` with a random `KATECODE_MCP_TOKEN` (env, not argv); it serves MCP Streamable HTTP (`MCPHttpServer`: POST /mcp, JSON responses, 202 for notifications, 405 for GET/DELETE, 401 without `Authorization: Bearer <token>`, Content-Length bodies only, 127.0.0.1) and prints `PORT <n>`. ssh gets `-o ControlPath=none -o LogLevel=INFO -R 0:127.0.0.1:<n>` (a connection of its own: through a shared ControlMaster ssh does not print the allocated port and the forward outlives the agent; `LogLevel=ERROR` in ssh_config hides the line; ssh takes an option's first value, so these beat the config files; checked against a real sshd. No ExitOnForwardFailure: a host refusing forwards still runs the agent); ssh's stderr `Allocated port <m> for remote forward to 127.0.0.1:<n>` (or `remote port forwarding failed`) gives `remoteMcpUrl()` = `http://127.0.0.1:<m>/mcp` (`remoteMcpReady()`). `ACPSession` waits for it (up to 10 s) before `initializeComplete()` and passes `{type: http, name: kate, url, headers: [Authorization]}` when the agent advertises `mcpCapabilities.http` (claude-agent-acp does). The forwarded port is open to every user of the host: hence the token. In remote mode `MCPServer` (`setRemote(RemotePathMap)`) maps `file_path` (must be absolute on the host) to the local path, lists only the host's open documents (as host paths), translates messages back (not file contents) and drops `katecode_paste_to_terminal` (Kate's terminal is local). Protocol version: the client's if 2025-06-18/2025-03-26/2024-11-05. In remote mode the tool descriptions say that the mount lags behind the host (no "always use instead of Read"). `KATECODE_MCP_LOG=1` logs each HTTP response on stderr. Tested: `test_remotefs.py` (fake ssh prints the allocated port = the local one, the sandbox shares the network), a real `ssh -R` to yyc-ms with curl from there, the real claude-agent-acp's MCP client in the sandbox (initialize, notification, GET 405 tolerated, tools/list; it asked for a newer protocol version and accepted 2024-11-05), and the offscreen Kate run

- Installing a missing agent (`AgentInstaller`, `src/acp/AgentInstaller.{h,cpp}`): when a remote agent exits 127, `ACPService::remoteAgentMissing()` (→ `ACPSession`, not `SummaryGenerator`/`ACPSessionDeleter`) lets the chat's failure notice offer "Install <agent> on <host>" (`ChatWebView::showReconnectPrompt(text, installLabel)`, disabled with the Reconnect buttons) if the provider has a `registryId` whose registry entry (`AgentIcons::registryEntry()`) has a `binary` build whose `cmd` file name is the provider's executable (`canInstall()`; the install is cancelled only when the chat's provider changes, not on other settings changes; npx/uvx-only agents and providers running another program get no offer), and this chat has not installed it on that host already (a second 127 then says the installed copy did not start). ### kate-code-helper (`remote-helper/`)
- Optional helper on the hosts of remote folders, so Kate Code can see the host's files as they are (the sshfs mount lags up to ~21 s) and get change notifications for open documents. Kate Code uses it for open documents (below); Kate's tools, `fs/*` for remote agents and the 22 s hold do not use it yet
- Kate Code side (`RemoteHelper`, `src/acp/RemoteHelper.{h,cpp}`, no KTextEditor; owned by `ACPSession`, started when the remote agent answers `initialize` (its ssh login done: no prompts side by side, nothing installed where the agent is missing), the setting `Remote/useHelper` is on (default; General tab "Remote Hosts") and a release is pinned (`RemoteHelper::builtinPin()`: `:/katecode/remote-helper-pin.json` = `src/acp/remote-helper-pin.json`, a placeholder without platforms until a release is pinned: then no helper). Never waited for; any failure is logged (`[RemoteHelper]`/`[ACPSession] Without kate-code-helper`) and the chat works as without it. One ssh connection (`KateRemote::sshHelperCommand()`: `ssh -T` with the agent's keepalive options and askpass environment) runs `remoteHelperLaunchScript()`: maps `uname -s`/`-m` (i386-i686 → linux-x86, armv6l/7l/8l → linux-arm; Windows `PROCESSOR_ARCHITECTURE`) to the pinned build, checks `~/.local/share/kate-code/helper/<version>/<platform>/kate-code-helper` (Windows `%LOCALAPPDATA%\kate-code\helper\...\kate-code-helper.exe`, run with byte-copied stdio like agents) against `programSize` and `programSha256` (sha256sum, shasum, openssl or Get-FileHash; size only without one) and execs it, else prints `kate-code-helper: install <platform>` and exits 97 (`RemoteHelperInstallNeeded`; 98 unsupported). On 97 (once per start) the pinned archive is downloaded here (https only; `~/.cache/kate-code/helper-downloads/<sha256>/`, refused unless it matches the pin), piped to `remoteHelperInstallScript()` (unpacked in a temp dir inside the platform directory, the program renamed into place: atomic, concurrent installs of one version write the same file) and the helper launched again. Lines before `hello` are skipped (60 s / 64 KiB limits); `hello` must have the pinned version and protocol and the `digest`/`watch` capabilities. A helper that was ready is restarted after its connection ends (5/10/20 s, 3 times; watches sent again). Errors with a null `id` fail all pending requests
- Open documents with the helper (`ACPSession::startRemoteHelper()`): the host's open documents are watched (set follows `documentCreated`/`documentWillBeDeleted`/`documentUrlChanged`); a `changed` notification opens the files through the mount at once in a thread (`kickMount()`: sshfs shows a host change about 1 s after the next open of the file, measured on yyc-ms; a stat or directory listing does not do it, and without an open sshfs answers from its cache for up to 20 s), is looked at 1.1 s later, digested, and a differing digest confirmed 1 s later (Kate's own saves notify too; the mount is fresh by then); modified documents are flagged (`setModifiedOnDisk`), unmodified ones reloaded once the mount shows the host's digest (`helperVerifyMount()`: read in a thread every 250 ms, so no reload of old contents; flagged instead after 25 s, as for a file rewritten with the same size within the same second, which sshfs's mtime (whole seconds) + size check never shows). `checkRemoteDocuments()` (after tool calls) uses the helper's digests when it is ready (and kicks differing files), else reads through the mount as before. Measured in an offscreen Kate against yyc-ms: reloaded 2.3-2.5 s after the host change, once
- Its own CMake project (`project(kate-code-helper VERSION ...)`), never `add_subdirectory`'d from the plugin: C++17 standard library + system APIs only (no Qt/KF), static release builds (Linux: musl in Alpine; Windows: static MSVC runtime; macOS: universal, ad-hoc signed by a post-build `codesign --force --sign -`: Apple's linker signs only the arm64 slice, and `codesign --verify` of the universal file then fails with "not signed at all")
- `remote-helper/PROTOCOL.md` is the contract (every implementation, e.g. a later JS one for Windows hosts with Node, follows it): newline-delimited JSON-RPC 2.0 on stdin/stdout, `hello` notification first (`protocol` major + `capabilities`), file contents base64, digests = git blob SHA-1 (as `KTextEditor::Document::checksum()` / `EditorDBusService::fileChecksum()`), `write` with `expectDigest` (refuse if changed), `watch`/`unwatch` + `changed` notifications (batched ~100 ms). Incompatible changes bump `ProtocolVersion` (`src/Server.h`); additions are new capabilities. `--version` prints `kate-code-helper <version> protocol <n>`
- Writes: temp file + rename (mode and owner kept; symlink targets replaced), in place for hard-linked files, unwritable directories, files whose owner cannot be restored, and (Windows) files open without delete sharing (`ReplaceFileW` otherwise)
- Watching: per directory (atomic saves replace the file): inotify (Linux; polling when out of watches), overlapped `ReadDirectoryChangesW` (Windows), polling every 0.5 s elsewhere (macOS); `KATE_CODE_HELPER_WATCH=poll` forces polling (tests)
- Tests: `tests/test_protocol.py <helper>` (ctest `protocol`) talks to the binary through the protocol only (Linux, macOS, Windows; native and polling watch). Checked here on Linux (glibc, dynamic and static) with ASan/UBSan and TSan. The Windows and macOS code has never been compiled (no cross toolchains here; only the workflow builds it, and it has not run yet), and the musl release builds, including the 32-bit x86/arm ones, have never been built or run
- Kate Code side tests: `RemoteLocationTest` (`remoteHelperPin`: validation incl. the committed pin file; `remoteHelperLaunch`: launch and install scripts under sh/bash/zsh with a stand-in helper: install needed, exec with stdio, tampered copy, archive without the program, unpinned platform; `windowsHelperScripts`: decoded script), `test_remotefs.py` `test_remote_helper` (`acpdriver --helper`; needs a built helper: configure with `-DKATE_CODE_HELPER_FOR_TESTS=<path>/kate-code-helper`, else skipped): wrong archive SHA-256 sends nothing, install + digest = git blob hash + a change reported as the local path, second start without install, a modified installed copy replaced from the cached download, a helper of another version refused. - Releases: `.github/workflows/remote-helper.yml` (path-filtered; tag `remote-helper-v<version>` must match `project()`'s version) builds on native runners (Linux x86_64/aarch64/x86/arm (ARMv6+ hard-float) static musl in Alpine via `docker run --platform`, the 32-bit ones natively on the x86_64/arm64 runners; macOS universal on an Intel runner, since GitHub's arm64 macOS runners are short of capacity (jobs waited 15 min and were cancelled): the x86_64 slice is tested there, the arm64 slice of the packaged archive in `macos-arm64`, which the release does not wait for), tests, packages `.tar.gz` per platform (only the program inside), writes `manifest.json` (platform keys as in the ACP registry, `-musl` aliases for Linux, both darwin keys → the universal archive; sha256, size, program, protocol) and `SHA256SUMS`, and publishes a release with `--latest=false` from the user's fork, github.com/yuyichao/kate-code. ### ACP Protocol
- JSON-RPC 2.0 over stdin/stdout with newline-delimited JSON
- Flow: `initialize` (protocolVersion: 1) → `session/new` (cwd, mcpServers) → `session/prompt`
- Streaming updates via `session/update` notifications with sessionUpdate types:
  - `agent_message_start`, `agent_message_chunk`, `agent_message_end`
  - `tool_call`, `tool_call_update`
  - `plan` (todos)
- Permission requests via `session/request_permission` with requestId that requires response

### ACP Provider Configuration
- Providers are defined by `ACPProvider` struct: id, description, executable, options, builtin flag

### Web Interface
- QWebEngineView loads HTML from Qt resources (qrc:/katecode/web/chat.html)
- JavaScript functions exposed: `addMessage()`, `updateMessage()`, `finishMessage()`, `addToolCall()`, `updateToolCall()`
- C++ calls JavaScript via `page()->runJavaScript()` with proper string escaping
- Tool and terminal output goes through `src/web/terminal-renderer.js` (a small terminal emulator: colours, cursor movement, 120 columns). Its input is decoded text, read by code point; wide characters (East Asian, emoji) take two columns, combining marks none. Rows that wrap at the width are marked and joined back into one line in the HTML (the `pre-wrap` boxes wrap it to the view's width; copying gives the original line); wrapping waits for the next character, as in terminals. Checked with node only (scratch cases), no test in ctest
- Drawing (`chat.js`): a message's HTML is rebuilt whole (markdown, highlighting, every tool call), so updates only mark it (`updateMessageDOM()`) and marked messages are drawn 16 ms later, once for all updates that came together; `scrollToBottom()` waits for that draw too. A message keeps its own element (`message.element`: ids can repeat, e.g. every "Generation stopped" notice is `sys_cancelled`). While a `session/load` replays history (`ACPSession::replayingChanged` → `ChatWebView::setReplaying()`), nothing is drawn; when it ends the newest messages are drawn at once (until twice the window's height, at least 30 ms' worth), the older ones in the background (30 ms per timer task, newest first; the page is the scroller, `document.scrollingElement`, kept at the bottom if it was there). Before, each replayed update redrew its whole turn's message (a replayed turn is one message, and task-notification cycles merge into it): measured in an offscreen Kate with the real claude-agent-acp loading a copy of a 57 MB session (8,700 updates, 390 messages): the view was busy for 10.5 s after the replay (ready at 2 s); now the newest message shows in ~90 ms, scripts wait at most ~100 ms and all is drawn by ~4 s, with the same text as before
- CSS uses CSS variables for theming (ready for KDE color injection in Phase 4)
- Responsive layout with message bubbles, tool call display, and streaming indicator
